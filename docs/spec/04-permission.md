# 04 · 应用、功能模块与角色

## 1. 目标

管理员不懂权限码也能配好角色：内置角色开箱即用；按“功能模块 × 四档”配置；菜单与权限码以代码为准。

## 2. 三层结构

```
应用 app（权限码的命名空间；用户看到的导航见 3.1）
 └─ 功能模块 feature（四档：无 / 查看 / 编辑 / 管理）
     └─ 动作 action（查 view · 增 create · 改 update · 删 delete · 导入 import · 导出 export）
          → 权限码 `{app}:{feature}:{action}`
```

| 档位          | 包含动作                 |
| ------------- | ------------------------ |
| 无 none       | —                        |
| 查看 view     | view                     |
| 编辑 edit     | view、create、update     |
| 管理 manage   | 该功能模块声明的全部动作 |
| 自定义 custom | 单独勾选的动作           |

每个功能模块只声明自己用到的动作，例如“学年学期”没有导入导出。

另有两个扩展动作，只在需要的功能模块中声明，并归入“管理”档（自定义档位时可单独勾选）：

| 动作                     | 用于                           |
| ------------------------ | ------------------------------ |
| `approve` 审核           | 学校服务开通审核、转学确认     |
| `sensitive` 查看敏感信息 | 学生、教师的证件号与手机号全文 |

### 3.1 模块、分组与菜单（用户看到的导航）

上表的“应用”是权限码的命名空间（`应用:功能模块:动作`），不直接显示给用户。用户看到的是 **模块 → 分组 → 菜单** 三层，各身份使用同一套名称，区别只在能看到哪些菜单、菜单里能看到哪些数据。

选择组织后进入“选择模块”页，一个模块一张卡片；只有一个可用模块时跳过该页。运动业务（跳绳、跑步等）以后各自是一个模块。

**基础信息模块 `base`**（company · bureau · agent · school · teacher）

| -------- | ---------- | --------------------------------------- | ------------------------------------------------ |

规则：

- 每个模块的侧栏第一项固定是“工作台”，登录即可用，不对应功能模块，也不在“菜单设置”和角色配置里出现（spec 13 第 2 节）。
- 分组名固定四个字；菜单名在 `packages/contracts` 中声明，一处改名处处生效。
- 模块可见 = 该模块下至少有一个菜单可见；菜单按对应功能模块至少为“查看”过滤，学校类身份还需满足对应应用的开通条件（spec 07）。导航模块不替代 `school_apps` 的应用权限命名空间。
- 公司的“超级管理员”角色能看到两个模块的全部菜单。
- “角色模板”是各组织类型的内置角色。公司超级管理员可以在界面上修改内置角色的默认数据范围和各菜单档位（规则见第 6.1 节）；各组织自己的管理员仍然不能改内置角色。

## 4. 代码声明（以代码为准）

`packages/contracts/src/apps/*.ts` 声明应用、功能模块、动作、菜单与内置角色档位：

```ts
export const schoolApp = defineApp({
  code: "school",
  name: "学校基础数据",
  icon: "school",
  identityTypes: ["school", "teacher", "company", "agent"],
  features: {
    student: {
      name: "学生",
      actions: ["view", "create", "update", "delete", "import", "export"],
    },
    // …
  },
  menus: [
    {
      key: "students",
      name: "学生管理",
      path: "/students",
      feature: "student",
    },
    // …
  ],
});
```

部署时 migrate 任务同步到 `apps`、`features`、`menus` 表：新增插入、删除的标记下线、已有的更新；后台改过的显示名称、排序、图标、显隐单独存在 `menu_overrides`，不被覆盖。

## 5. 数据

| 表                      | 关键字段                                                                                                                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps`                  | code、name、icon、identity_types[]、sort、status                                                                                                                                                     |
| `features`              | app_code、code、name、actions[]                                                                                                                                                                      |
| `menus`                 | app_code、parent_key、key、name、path、icon、feature、client（admin · mobile）、sort                                                                                                                 |
| `menu_overrides`        | menu_key、display_name、sort、icon、hidden                                                                                                                                                           |
| `roles`                 | kind（preset · custom）、base_role_id、identity_type、org_id（空为内置）、code（系统生成）、name、data_scope（all · dept_and_below · dept · personal；student 固定 self，parent 固定 child）、remark |
| `role_grants`           | (role_id, app_code, feature_code)、level、actions[]（level=custom 时）                                                                                                                               |
| `preset_role_overrides` | role_id（内置角色）、data_scope（空表示沿用代码）、grants jsonb（只存与代码默认不同的功能模块：level、actions[]）、updated_by、updated_at、version                                                   |

内置角色的默认档位写在代码里；超级管理员在界面上改过的部分存在 `preset_role_overrides`，部署同步时不被覆盖（与 `menu_overrides` 同样的做法）。`role_grants` 只存自定义角色与其基础角色不同的行。

内置角色的最终档位 = 代码默认，被 `preset_role_overrides` 中的同名功能模块覆盖。

自定义角色的最终档位 = 基础内置角色的最终档位，被 `role_grants` 中该自定义角色的同名功能模块覆盖。内置角色的最终数据范围优先使用模板覆盖值，未覆盖时沿用代码默认；自定义角色使用自己配置的数据范围。

### 6.1 超级管理员修改内置角色（平台管理 › 角色模板）

1. 只有持有 `system:preset-role:update` 的公司身份可以改，默认只有“超级管理员”角色有这个权限。
2. 可以改的：默认数据范围、每个功能模块的档位与细调动作、角色说明。不能改的：角色属于哪类身份、角色编码；不能在界面上新增或删除内置角色（仍由代码声明）。
3. “超级管理员”这个角色本身不能改，始终是全部管理，避免把自己锁在外面。
4. 修改对**所有组织**里使用这个角色的人立即生效：保存前界面显示受影响的组织数和人数，并要求二次确认；保存后清除这些身份的权限与数据范围缓存。
5. 基于该内置角色另存的自定义角色：没有单独调整过的功能模块跟着变，调整过的保持不变。
6. 每个被改过的功能模块标“已改”，可以单项或整体“恢复默认”（删除对应的覆盖行，回到代码默认）。
7. 代码里新增的功能模块，没有覆盖行时用代码默认；代码删除的功能模块，对应覆盖行在同步时清理。
8. 每次修改写审计，记录修改前后的差异；更新带 `version` 做乐观锁。
9. 代理商授权上限、学校已开通模块、服务状态这些限制不受影响（第 9 节的交集照常计算），所以调高内置角色的档位不会让代理商越过学校的授权。

| ----------- | ---------------------------- | ----------------------------- | -------------------------------------------------------------------------- |

| GET         | `/menus/current?module=`     | 登录                          | 某模块的“分组 → 菜单”树（已按权限、学校开通情况过滤）                      |

## 8. 分级管理

1. 只能管理本组织的成员与自定义角色；公司超管可管理所有组织。
2. 上级教育局管理员可为下级教育局开通首个管理员。
3. **不高于自己**：分配或编辑角色时，每个功能模块的档位不能超过操作人的档位；数据范围不能比操作人更宽。
4. 不能修改自己的角色；每个组织至少保留一名在 `org:member` 与 `org:role` 上都为“管理”档的成员。
5. 各组织的管理员不能编辑、删除内置角色，只能“基于它另存为自定义角色”。内置角色只能由公司超级管理员在“角色模板”里修改（第 6.1 节），任何人都不能删除。
6. 角色正在被使用时不能删除，需先替换。

## 9. 权限计算

```
身份权限码 = ⋃（每个角色：每个功能模块的最终档位 → 动作 → 权限码），每个权限码记录授予它的角色中最宽的数据范围
请求某学校时实际权限 = 身份权限码
                    ∩ 该学校已开通应用的权限码（学校类身份、以及 company/agent 进入学校时）
                    ∩ 代理商授权上限（agent 身份）
                    ∩ 服务状态限制（宽限期只保留 view、export）
```

## 11. 验收标准

- 新建研发部员工自动获得“研发人员”角色，进入选择模块页只看到其可用模块。
- 学校管理员无法创建档位高于自己的自定义角色。
- 代码新增一个功能模块并发布后，内置角色在无模板覆盖时按代码档位生效；自定义角色未调整该功能时跟随基础角色最终档位。
- 后台改过的菜单名称在下次发布后保持不变。
- 超级管理员把“年级组长”的学生管理从查看改为编辑后，所有学校的年级组长下一次请求即可编辑；下次发布后这项修改仍在；点“恢复默认”后回到查看。
- 学校管理员调用修改内置角色的接口返回 403；修改“超级管理员”角色返回 11107。

### 角色模板接口补充约定（T-041）

- `GET /preset-roles` 返回数组，包含代码默认值、最终值、每项已改标记、可操作动作及使用数量；修改和影响预览提交全部功能模块的档位，未授权模块显式提交 `none`，拒绝遗漏、重复功能和未声明动作。
- 保存体为 `{ version, dataScope, remark, grants: [{ app, feature, grant }] }`；影响预览使用同一请求体，返回受影响的组织、账号、身份数量和各关联角色的菜单增减。使用数量包含直接分配和基于模板派生角色的去重身份，排除软删除身份、组织及账号。
- 恢复体为 `{ version, feature?: { app, feature } }`；指定功能只恢复该项，省略时同时恢复全部档位、数据范围和说明。
- `version` 使用内置角色的资源版本。每次模板保存或恢复递增角色版本，覆盖全部删除后版本也不会回退；部署同步不得重置版本。覆盖表仅保存差异，全部恢复后删除覆盖记录。
- 研发人员的 `system:preset-role` 默认为查看，作为“system 管理”的明确例外；默认修改权只给公司超级管理员。
